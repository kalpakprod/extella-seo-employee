# Blueprint: универсальный SEO-сотрудник 2.0

## Статус документа

- Дата: 30.08.2026.
- Статус: дизайн утверждён пользователем, реализация завершена; подтверждения закрытого пилота ведутся в `docs/verification/v2-progress.md`.
- Продукт: Extella «SEO-сотрудник: аудит и контроль».
- Целевой выпуск: `2.0.0`, закрытый пилот.
- Предыдущий проверенный выпуск: `1.0.0`.

Настоящий Blueprint определяет техническую композицию универсального SEO-сотрудника. Feature Contract определит пользовательское обещание, Component Contracts определят исполняемую логику, а Contract Tests будут сформированы из Component Contracts. Blueprint НЕ заменяет эти документы и НЕ вводит скрытое пользовательское поведение.

## 1. Решение

Продукт ОБЯЗАН расширить существующую композицию Agent Zero, CrawlSEO и SEOmator. Продукт НЕ ДОЛЖЕН заменять её новым агентным фреймворком или SEO-монолитом.

Универсальность означает применимость к разным отраслям и типам сайтов через детерминированные профили и планы аудита. Она НЕ означает неограниченный обход, гарантированный рост трафика, замену всех функций SEO-команды или право автономно изменять внешние системы.

Бесплатное self-hosted ядро ОБЯЗАНО работать без Google Search Console, DataForSEO и других платных источников. Платные и OAuth-источники МОГУТ подключаться отдельно и НЕ ДОЛЖНЫ становиться условием технического аудита.

## 2. Основание выбора

| Вариант | Режим Wheel | Gain | Cost | Решение |
|---|---|---:|---:|---|
| Расширить текущие CrawlSEO и SEOmator | `compose` | 5 | 2 | Выбран |
| Передать Agent Zero прямое управление всеми MCP-tools | `extend-core` | 5 | 3 | Отклонён из-за снижения детерминизма и проверяемости |
| Заменить продукт на OpenSEO | `replace` | 5 | 5 | Отклонён из-за миграции проверенного контура, дублирования UI/state и обязательного DataForSEO |

Зрелость по свежей проверке Wheel: CrawlSEO — `B`, SEOmator — `C`, OpenSEO — `A`. Более высокая зрелость OpenSEO не компенсирует миграционный и операционный зазор существующего релиза из 65 payload-файлов и семи контейнерных сервисов.

## 3. Переиспользуемые компоненты

Продукт ОБЯЗАН сохранить:

- Experts `seo_employee_run` и `seo_employee_state`;
- Extella bridge и singular `target`;
- URL validation, DNS resolution и SSRF-защиту;
- общий deadline и отмену source workers при timeout/disconnect;
- атомарную запись состояния, отчётов, истории и evidence;
- блокировки, суточную дедупликацию и восстановление stale lock;
- сравнение `new`, `fixed`, `unchanged`;
- Agent Zero transport и строгий структурированный ответ;
- состояния `empty`, `running`, `ready`, `partial`, `failed`;
- переносимый Docker Compose, backup и restore-check.

Первый этап реализации НЕ ДОЛЖЕН добавлять новый runtime-компонент. SiteOne Crawler, Unlighthouse, SerpBear, changedetection.io и отдельные GSC-коннекторы остаются кандидатами только для будущего доказанного зазора.

## 4. Поддерживаемые профили

`IndustryProfile` ОБЯЗАН принимать одно из следующих значений:

1. `service_b2b` — услуги и B2B;
2. `ecommerce` — интернет-магазин;
3. `local_business` — локальный бизнес;
4. `content_media` — медиа и контентный проект;
5. `saas_marketplace` — SaaS или маркетплейс.

Профиль ОБЯЗАН определять только применимость правил, категории аудита и порядок приоритета. Профиль НЕ ДОЛЖЕН менять проверенный факт, подменять данные источника или разрешать модели выбирать собственный план аудита.

Каждая цель ОБЯЗАНА дополнительно хранить язык, регион, тип сайта, бизнес-цель, расписание и crawl budget. Значения отрасли, языка и региона, передаваемые модели, ОБЯЗАНЫ проходить валидацию и нормализацию.

## 5. Режимы продукта

Продукт ОБЯЗАН поддерживать:

1. `full_audit` — полный разрешённый аудит выбранной цели;
2. `daily_monitor` — суточный контроль новых, исправленных и оставшихся проблем;
3. `search_performance` — анализ GSC, позиций и opportunities при наличии источника;
4. `work_plan` — формирование приоритетного плана и контентных заданий из подтверждённых данных.

Отсутствие OAuth или платного источника НЕ ДОЛЖНО блокировать `full_audit` и `daily_monitor`. Недоступный режим ОБЯЗАН возвращать `not_configured` с причиной и инструкцией подключения.

## 6. Компоненты доменного ядра

### 6.1 Profiles

`experts/seo_employee_profiles.py` ОБЯЗАН содержать `IndustryProfile` и `AuditPlan`. `AuditPlan` ОБЯЗАН определять:

- применимые категории правил;
- обязательные и опциональные источники;
- максимальное число страниц;
- стратегию выборки performance-проверок;
- deadline источников;
- политику подтверждения находок.

### 6.2 Rule Catalog

`experts/seo_employee_rules.py` ОБЯЗАН содержать версионируемый canonical rule catalog. Для каждого правила ОБЯЗАТЕЛЬНЫ:

- `rule_key`;
- применимые профили;
- severity;
- нормализованный проверяемый факт;
- способ исправления и повторной проверки;
- source-rule mappings;
- corroboration policy;
- версия правила.

Неизвестный source rule НЕ ДОЛЖЕН молча исчезать. Он ОБЯЗАН учитываться в `coverage.unmapped_rules`, но НЕ ДОЛЖЕН становиться пользовательской задачей до регистрации в каталоге.

### 6.3 Source Adapters

`experts/seo_employee_sources.py` ОБЯЗАН определить адаптеры CrawlSEO, SEOmator и опциональных источников. Каждый адаптер ОБЯЗАН:

- объявлять capabilities;
- валидировать входной план и выходной payload;
- извлекать occurrences;
- возвращать точный coverage;
- различать `ok`, `not_configured`, `unavailable`, `failed`, `unsupported`;
- не скрывать WAF, CAPTCHA, 403, 429, 503 и timeout.

### 6.4 Targets

`experts/seo_employee_targets.py` ОБЯЗАН реализовать `extella.seo_employee_config.v2`, миграцию v1 и per-target paths. Каждая цель ОБЯЗАНА иметь стабильный `target_id`. Baseline, daily index, lock, state, history и последний report ОБЯЗАНЫ быть изолированы по `target_id`.

## 7. Поток данных

```text
Extella UI
  -> validated target + run mode
  -> deterministic AuditPlan
  -> CrawlSEO and SEOmator adapters
  -> canonical Rule Catalog
  -> Evidence Merger
  -> Coverage + Priority Queue
  -> sanitized model input
  -> Agent Zero explanation and work plan
  -> atomic state/report/history
  -> Extella UI
```

Модель НЕ ДОЛЖНА определять наличие дефекта. Модель МОЖЕТ объяснять деловое последствие, минимальное исправление, порядок выполнения и контентное задание только по разрешённым полям.

Модель НЕ ДОЛЖНА получать сырые страницы, HTML, заголовки HTTP, cookie, параметры запроса, токены, OAuth-данные, содержимое форм или идентичность аккаунта.

## 8. Источники и покрытие

### 8.1 Бесплатное ядро

- SEOmator: multi-page технический, on-page, content, schema, performance, accessibility и GEO audit.
- CrawlSEO: crawler, технические issues, Core Web Vitals, history и локальные opportunities.

### 8.2 Опциональные источники

- Google Search Console: queries, pages, clicks, impressions, CTR и position.
- DataForSEO или совместимый провайдер: keyword volume, competitor/SERP и backlinks.

Опциональный источник ОБЯЗАН иметь отдельные credentials, budget cap, health и disclosure. Неуспех опционального источника НЕ ДОЛЖЕН превращать полный бесплатный технический аудит в `failed`.

`coverage` ОБЯЗАН содержать planned pages, crawled pages, sampled pages, применённые категории, выполненные источники, недоступные источники и unmapped rules.

## 9. Лимиты закрытого пилота

- Значение по умолчанию: 25 страниц на цель и Запуск.
- Жёсткий предел: 100 страниц на цель и Запуск.
- SEOmator ОБЯЗАН выполнять все 20 категорий, но Performance/JS-rendering ОБЯЗАНЫ проверяться максимум на пяти страницах: главная страница и до четырёх indexable HTML URL с минимальной глубиной, отсортированных по `(depth, URL)`.
- Пользователь НЕ ДОЛЖЕН иметь возможность превысить жёсткий предел через UI, Expert params или config-файл.
- Изменение предела требует нового benchmark и обновления Service Contract.

Одностраничный режим ОБЯЗАН сохранить общий deadline 180 секунд и source deadline 120 секунд. Multi-page режим ОБЯЗАН иметь общий deadline 900 секунд и source deadline 720 секунд. Любой адаптер ОБЯЗАН использовать только оставшийся общий бюджет и отменять дочернюю process group при его исчерпании.

Очередь ОБЯЗАНА выполнять source-heavy запуски последовательно на одном worker. Очередь ОБЯЗАНА храниться атомарно в `state/queue.json` и восстанавливаться после перезапуска. Параллельные запросы одной цели ОБЯЗАНЫ дедуплицироваться. Запросы разных целей ОБЯЗАНЫ ожидать FIFO-очередь, а не завершаться неясным `worker_busy`.

## 10. Состояния и базовая линия

- `ready`: все обязательные источники выполнили весь AuditPlan.
- `partial`: часть запланированного покрытия потеряна, но подтверждённых данных достаточно для ограниченного отчёта.
- `failed`: подтверждённого результата недостаточно.

`partial` НЕ ДОЛЖЕН объявлять исчезнувшую находку исправленной и НЕ ДОЛЖЕН заменять baseline. Baseline ОБЯЗАН обновляться только завершённым `ready` для той же цели, совместимого плана и той же major-версии Rule Catalog.

Corroboration ОБЯЗАНА определяться конкретным правилом. Наличие двух любых источников НЕ ЯВЛЯЕТСЯ достаточным условием `verified`.

## 11. Схемы и совместимость

- Конфигурация: `extella.seo_employee_config.v2`.
- Состояние: `extella.seo_employee_state.v2`.
- Отчёт: `extella.seo_employee_report.v2`.

Expert names, app scopes, Extella target semantics и базовые методы `run`/`state` ОБЯЗАНЫ сохраниться. Новые поля запроса ОБЯЗАНЫ быть опциональными и иметь безопасные значения по умолчанию.

Мигратор ОБЯЗАН преобразовать v1 в одну цель `service_b2b` с режимом `daily_monitor`, прежним URL, расписанием и timezone. После миграции прежний одностраничный fixture ОБЯЗАН сформировать ту же задачу `meta-description-missing`; отличие допускается только в новых полях envelope v2.

Миграция ОБЯЗАНА быть атомарной, идемпотентной и сохранять исходный v1-файл до успешной проверки v2.

## 12. Agent Zero

Agent Zero ОБЯЗАН оставаться за детерминированным оркестратором и НЕ ДОЛЖЕН получать произвольный shell, browser или unrestricted MCP access.

Agent Zero ОБЯЗАН получать один versioned structured input и возвращать versioned structured output. Разрешённые результаты:

- `business_impact` без неподтверждённых метрик;
- `minimal_fix`;
- `verification`;
- `priority_reason`;
- `content_brief`, только когда его входные факты и поисковые данные перечислены в evidence.

Пользователь выбирает provider/model/auth route. Каждый точный маршрут ОБЯЗАН пройти отдельный live E2E. Автоматический model fallback ЗАПРЕЩЁН.

## 13. Действия и подтверждение

Версия 2.0 ОБЯЗАНА формировать `action_proposal` как отдельный артефакт. Предложение ОБЯЗАНО содержать точную цель, изменение, доказательство, preview, способ отката и срок действия.

Наличие предложения НЕ ЯВЛЯЕТСЯ разрешением на запись. Внешняя запись МОЖЕТ выполняться только адаптером, который имеет собственный Feature/Service Contract, минимальный scope и явное подтверждение пользователя для конкретного предложения.

Если такой адаптер не настроен, интерфейс ОБЯЗАН предлагать ручное выполнение или копирование инструкции. Версия 2.0 НЕ ОБЯЗАНА включать CMS-коннектор.

## 14. Безопасность

Продукт ОБЯЗАН сохранить:

- запрет private, loopback, link-local, control и credential-bearing URL;
- проверку каждого redirect и DNS resolution;
- разрешённые HTTP-методы и фиксированные internal routes;
- read-only containers, dropped capabilities и разделённые сети;
- secret files вместо env/log payloads, где это уже используется;
- нулевую запись во внешние системы без отдельного подтверждения;
- cancellation дочерней process group при disconnect/timeout.

Перед первым аудитом цели пользователь ОБЯЗАН подтвердить право владения сайтом или полномочие на аудит. UI и backend ОБЯЗАНЫ применять одно и то же требование.

## 15. Ошибки и деградация

WAF, CAPTCHA, 403, 429, 503, robots denial и timeout ОБЯЗАНЫ иметь отдельные машинные коды и понятные пользовательские сообщения. Они НЕ ДОЛЖНЫ маскироваться как отсутствие SEO-дефектов.

Ошибка модели НЕ ДОЛЖНА уничтожать подтверждённые findings. Продукт ОБЯЗАН вернуть детерминированные задачи без model-enriched полей и обозначить ограничение. Это НЕ является переключением на другую модель.

Ошибка одного сайта НЕ ДОЛЖНА повреждать очередь, baseline или состояние другой цели.

## 16. Пользовательский интерфейс

UI ОБЯЗАН предоставить:

- список целей и состояние каждой цели;
- создание и редактирование цели;
- профиль, язык, регион, бизнес-цель и crawl budget;
- режим запуска;
- coverage и ограничения;
- группы `new`, `fixed`, `unchanged`;
- до 10 приоритетных задач с evidence;
- `not_configured` для опциональных источников;
- очередь и следующий Запуск;
- action proposal и отдельное подтверждение.

UI НЕ ДОЛЖЕН обещать полный аудит, если coverage неполон. Название продукта ОБЯЗАНО сопровождаться маркировкой `Closed Pilot` и точным описанием включённых capability packs.

## 18. Проверка

Contract Tests ОБЯЗАНЫ покрывать:

- миграцию v1 → v2 и повторный запуск миграции;
- каждый профиль на фиксированных HTML fixtures;
- multi-page limits 1, 25 и 100;
- rule-specific corroboration и unmapped rules;
- required/optional source policy;
- WAF, CAPTCHA, 403, 429, 503, robots и timeout;
- `partial` без ложного `fixed` и без замены baseline;
- per-target history, queue, locks и daily deduplication;
- sanitizer, secret scan и отсутствие raw pages в model input;
- model failure без потери deterministic findings;
- frontend/backend ownership gate;
- action proposal без неразрешённой записи;
- backup, restore-check, restart и cancellation;
- Extella validators и UI/API contract.

Перед утверждением релиза ОБЯЗАТЕЛЬНЫ:

1. свежий полный локальный test run;
2. deterministic clean build;
3. secret scan runtime/page archives;
4. clean extraction и Compose validation;
5. CT160 E2E для всех пяти профилей;
6. независимый read-only review полного diff;
7. точный список `verified` и `not_verified`.

## 19. Критерии готовности 2.0

Версия 2.0 считается готовой к закрытому пилоту только если:

- все пять профилей создают детерминированный AuditPlan;
- бесплатный аудит работает без GSC и платных ключей;
- один Запуск обрабатывает до 100 страниц без нарушения deadline, memory limit и cancellation contract;
- несколько целей не смешивают состояние и baseline;
- coverage исключает ложное ощущение полноты;
- Agent Zero не придумывает факты и не получает запрещённые данные;
- ни одно действие не записывается без отдельного подтверждения;
- старый v1 fixture мигрирует и сохраняет исходную задачу;
- новый архив разворачивается на чистом Linux amd64-хосте;
- границы пилота и неподтверждённые коммерческие утверждения явно перечислены.

## 20. Не входит в 2.0

- неограниченный обход всего интернета;
- собственная SERP- или backlink-база;
- массовый прямой scraping Google;
- покупка ссылок и outreach;
- автономная публикация контента;
- универсальный CMS-коннектор;
- автоматический model fallback;
- обещания трафика, позиций, лидов или выручки;
- enterprise compliance без отдельной проверки.
