# Production Readiness Plan: SEO Employee → публичный production

## Goal

Довести продукт от текущего `SHIP_CLOSED_PILOT` (2.0.3, ветка `release/2.1.0`) до состояния,
в котором допустимо заявлять публичный production: закрытые hygiene-блокеры, закалённый
контур, воспроизводимый релизный гейт и честные границы в релизных заметках. Магазинный
трек (публикация листинга) ведётся по соседнему плану и здесь только стыкуется.

## Success Criteria

1. В дереве и истории нет живых секретов; засвеченный токен отозван; ротация токена —
   документированная процедура с drill.
2. Контур переживает базовые прод-нагрузки и атаки: rate limits, access-логи без секретов,
   расширенный health/метрики, TLS на границе, `agent-zero` зажат или исключение
   задокументировано.
3. Бэкапы: расписание, заявленные RPO/RTO, drill восстановления из снапшота пройден.
4. Релизный гейт воспроизводим одной цепочкой: сюиты → детерминированная сборка со
   сверкой хешей → `selfcheck.py → READY` → прогон точного релизного архива → чистая
   комната → зелёные upstream-гейты.
5. Версия 2.1.0 выставлена во всех источниках правды; release notes фиксируют границы
   (BYOK-источники, плавающее model enrichment); вердикт сменён с `SHIP_CLOSED_PILOT`
   только человеком по чек-листу.
6. Стейджинг-хост поднят и подтверждает, что продукт ставится и работает вне ноутбука
   разработчика.

## Constraints And Non-goals

- Контракты репо: модель выбирает пользователь, автоматический fallback запрещён,
  no-tools для Agent Zero; продуктовый Python — только stdlib, без новых зависимостей.
- `evidence/` — дом для E2E-паков (исключена из релизного payload, золотые фикстуры
  гейтов не трогать).
- Non-goals: SaaS-мультитенантность/RBAC/биллинг, запись в CMS, зашивание моделей,
  GSC/OAuth-лейны (отложены за гейт D2 из релизного плана), DonSeTch-интеграция.
- Коммерческий трек (права/IP, проценты, rails/KYC, deck, LOI) ведёт человек и не
  блокирует технические фазы, но блокирует смену вердикта.

## Key Decisions

- **R1. База решений D1–D5 из `docs/plans/2026-09-14-production-release.md` принимается
  как есть** (путь публикации `add-version-stream`, GSC за гейтом, версия 2.1.0,
  файловая ротация с рестартом, минимальный CI). Причина: решения свежие (сегодня),
  обоснованные, альтернативы в том плане уже разобраны.
- **R2. Порядок: hygiene → hardening → gate → store.** Причина: секреты и грязное
  дерево — единственные необратимые риски (утечка, потеря работы); магазинная версия
  неизменяема (H8), поэтому всё чинится до создания версии 2.1.0.
- **R3. Плавающее model enrichment — известное ограничение, не блокер.** Причина:
  детерминированные evidence сохраняются всегда, ограничение честно фиксируется в
  отчёте (`limitation`), лечится на стороне провайдера/ретраев, а не архитектуры.
  Альтернатива «добиться 10/10» отвергнута: внешний флак, гарантий дать нельзя.
- **R4. Стейджинг обязателен до заявления production, но не до питча.**
  Причина: питч идёт с локального демо + evidence; заявление production требует
  доказательства установки вне ноутбука. Дефолт — дешёвый VPS с TLS reverse proxy
  (см. Open Questions).
- **R5. Публикация коммитов — пофазно.** Каждый Phase ниже — отдельный коммит(ы) в
  порядке фаз; схлопывать запрещено (связывает исполнение правилом plan skill).

## Recommended Approach

Четыре фазы со строгим порядком. Phase 0 — сегодня, руками отзывается токен и
фиксируется дерево. Phase 1 — код закалки с тестами на каждый механизм. Phase 2 —
механический гейт, который либо весь зелёный, либо релиза нет. Phase 3 — стык с
магазинным планом и смена вердикта человеком. Параллельно человек ведёт коммерцию.

## Work Plan

### Phase 0 — Hygiene и заморозка, P0 (сегодня)

- **H0.1 Отзыв и ротация токена (человек + агент).** Человек отзывает засвеченный
  токен на стороне, выдавшей его; агент генерирует новый файловый секрет,
  перезапускает контур, проверяет старый → 401, новый → 200. Затем агент добавляет
  в `deploy/prepare.py` флаг/команду ротации (расширение `ensure_generated_secret`,
  D4) + доку с drill-шагами.
- **H0.2 Фиксация дерева (агент, пуш — человек).** Коммит на `release/2.1.0` строго
  двумя коммитами: (1) доки/evidence/CI (`AGENTS.md`, `.github/`, `docs/plans/`,
  `docs/verification/`, `evidence/e2e-*`); (2) код и сборки (`deploy/`, `dist/`,
  `release-manifest.json`, `tests/`). Пуш — только по явной команде человека.
- **H0.3 Scope freeze.** Всё вне этого плана и релизного плана — в Wave 6+.
- Приёмка: `git status --short` пуст (кроме оговорённого); drill ротации пройден;
  секретов в `git log -p` и логах нет (grep по `token|secret|password|api[_-]?key`).

### Phase 1 — Закалка контура, P1 (агент)

- **H1.1 Rate limits + access-логи + health/метрики.** Лимиты на API в `server.py`/
  `gateway.py` (429 при превышении), access-логи с соблюдением H71 (без секретов),
  расширенный `/health` (версия, состояние очереди, зависимости). Тесты: превышение
  лимита → 429; секрет из заголовка не попадает в лог; health отвечает за <1с.
- **H1.2 Agent Zero.** Зажать сервис в `deploy/compose.yaml` (`read_only`, `cap_drop`,
  `healthcheck`, `user`) либо зафиксировать исключение с причиной в `deploy/README.md`.
  Проверка: `compose config -q` + `compose up` + health зелёный.
- **H1.3 Бэкапы.** Расписание (cron/systemd-timer, док), заявленные RPO/RTO в
  `deploy/OPERATIONS.md`, drill: `create → verify → restore-check` на копии с
  независимым страховочным снапшотом. Приёмка — транскрипт drill.
- **H1.4 TLS ingress-ранбук + стейджинг.** Референсный reverse proxy (TLS, внешняя
  авторизация) как док + проверки; подъём стейджинга, установка по документации
  без импровизаций, `health/state` извне. Приёмка — URL стейджинга и транскрипт.
- Приёмка фазы: CI зелёный; `curl`-пробы подтверждают 429/логи/метрики; drill
  восстановления выполнен; стейджинг отвечает.

### Phase 2 — Релизный гейт 2.1.0 (агент + человек на вердикте)

- **H2.1 Бамп версии.** Чек-лист: `runtime/product/server.py` (VERSION),
  `MANIFEST.yaml`, `listing.json`, `deploy/compose.yaml` (теги образов),
  `tools/build_release.py` (VERSION), регенерация `release-manifest.json`,
  `automation_passport.yaml`, оба README. Тест-инвариант: все источники сходятся
  (расширить `test_packaging.py` при необходимости).
- **H2.2 Полная верификация одной цепочкой.** Сюиты → детерминированная пересборка
  со сверкой хешей с `dist/build.json` → `selfcheck.py → READY` → прогон точного
  релизного архива (тесты + live probe + backup/restore-check) → чистая комната
  (`не установлено → готово → рестарт → готово`) → 12/12 upstream-гейтов.
- **H2.3 Release notes.** Что вошло, границы (BYOK не подключён, enrichment может
  быть частичным, одна реплика/FIFO), известные ограничения. Без неподтверждённых цифр.
- Приёмка: вся цепочка зелёная за один проход; evidence-пак гейта сохранён в
  `evidence/`; человек подтверждает вердикт.

### Phase 3 — Магазин и вердикт (стык с релизным планом)

- Выполнить Wave 1 релизного плана (`tools/publish_store.py` → предрелиз →
  self-purchase → чистая комната) после снятия `FORBIDDEN_TIER` с фаундерами.
  Publish нажимает человек (H26). Затем смена вердикта `SHIP_CLOSED_PILOT` →
  production по чек-листу H2.2 + подписанная коммерция.
- Приёмка: листинг видим, `app-archive` 200 с побайтовым SHA-256, скоупы без
  лишнего, эксперты вызываются; вердикт сменён.

## Risks / Rollback

- Неизменяемость версий (H8): провал → следующий номер, никогда тот же; публикация
  обратима (`published: false`).
- Дрейф контракта выкладки: пинить ревизию ранбука, сырой SSE — в файл до разбора.
- Кросс-вольюмный restore нетранзакционный: drill только со страховочным снапшотом.
- Откат рантайма: предыдущий архив + биндинги сохраняются; откат = предыдущий тег.
- Человеческий трек (токен, деньги, Publish) может отстать — он вынесен из
  критического пути технических фаз, но блокирует Phase 3 и смену вердикта.
