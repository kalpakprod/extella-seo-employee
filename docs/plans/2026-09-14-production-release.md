# Production Release Plan: Extella SEO Employee 2.0.3 → 2.1.0

## Goal

Довести продукт от статуса `SHIP_CLOSED_PILOT` (2.0.3) до полного релиза: опубликованный листинг в магазине Extella, закалённый self-hosted прод-контур и закрытые коммерческие/питч-блокеры.

## Success Criteria

1. Магазин: предрелиз выложен, куплен себе на отдельном агенте, приёмка в чистой комнате пройдена, человек нажал Publish; архив и страница побайтово сверены с SHA-256, скоупы без лишнего.
2. Установка с нуля на чистой машине проходит по документации; first-bind устройства объяснён, все отказы — с явной причиной.
3. Прод-контур: зелёный CI, rate limits, access-логи и метрики, процедура ротации токена, расписание бэкапов с заявленными RPO/RTO, ранбук TLS/авторизации.
4. Полные сюиты, детерминированная сборка и прогон релизного архива на CT160 — всё зелёное.
5. Права, проценты и платежи зафиксированы письменно; измерены run cost и стоимость инфры; deck добран (конкуренция, GTM, ask, роадмап).

- Независимо перепроверено в этом окружении: Python 181/181, Node 64/64, `selfcheck.py → READY`, `manifest_check.py` — всё ok, пересборка детерминирована (хеши `c8beb289…`, `7ccaf62c…` совпали), `compose config -q` валиден, дерево чисто.
- Провал публикации 01.09: `POST /api/publish-stream` → `Errno2 .../archives/<uuid>.zip` (чат Dream Team, msg21); обход «без поля archive + rec_bundle» (msg22). Оба факта — из `result.json` экспорта чата.
- Ранбук выкладки от 03.09 (позже провала): магазин — `os.extella.ai`, заголовок `X-Extella-Token`, корректный путь — `POST /api/add-version-stream/{lid}` с SSE-потоком и терминальным `done/error`; версия неизменяема (H8); листинг несёт и страницу, и архив (H10); Publish жмёт человек (H26); сырой SSE сохранять в файл; приёмка — на отдельном агенте и в чистой комнате финальным ZIP. Источник: `RUNBOOK_STORE_PUBLISH.md` (см. Sources).
- Подтверждённые пробелы: нет CI; нет TLS/внешней авторизации в коробке; нет rate limits, логов доступа и метрик (поиск по `prometheus|grafana|sentry|opentelemetry|rate_limit|throttl` — 0 совпадений; `log_message` — no-op в `server.py`/`gateway.py`); единый статический токен без ротации (`prepare.py:63-70` только создаёт); бэкап исключает secrets/bindings/Agent Zero, restore нетранзакционный, расписания нет (`deploy/OPERATIONS.md:21`); `agent-zero` без read_only/cap_drop/healthcheck (`deploy/compose.yaml:90`); одна реплика, FIFO-очередь, E2E 25 страниц ≈ 569 c; нет pentest и Terms/Privacy; license review не проведён (`README.md:109`); GSC/OAuth/BYOK/user-домен — `not_configured`/`not_verified`; цена в листинге 0, TAM/спрос/юнит-экономика не верифицированы.
- `install.py:47-70`: сверка каждого файла по `release-manifest.json` (SHA-256), атомарное копирование, списки bindings/secrets — фундамент для чистой установки.
- Культура репо: контракты → тесты → реализация, без новых зависимостей в прод-Python (stdlib), детерминированные сборки, доказательства вместо заявлений.

## Constraints And Non-goals

- Не нарушать контракты: модель выбирает пользователь, автоматический fallback запрещён, no-tools для Agent Zero.
- Не добавлять зависимости в продуктовый Python; держать сборку детерминированной.
- Non-goals (половина — из совета, `reviews/openexecutive-council-2026-08-30.md:73`): DonSeTch-интеграция, SaaS-мультитенантность/RBAC/биллинг, база ключевых слов и ссылочный анализ, запись в CMS, зашивание моделей внутрь продукта.

## Key Decisions

- **D1. Путь публикации.** Рекомендуется первичный путь по ранбуку 03.09 (`add-version-stream`, SSE, предрелиз → покупка себе → чистая комната → Publish). Обход msg22 (без `archive` + bundle-установщик) — только fallback, если загрузка архива снова упрётся в серверную ошибку. Причина: ранбук авторитетен, датирован после провала и объясняет его (01.09 били в эндпоинт, которого в ранбуке нет).
- **D2. GSC/OAuth/BYOK в релизе.** Рекомендуется отложить за гейт Wave 6 (пост-релиз): требует внешних аппрувов и не блокирует технический аудит. Реверсивно решением на гейте.
- **D3. Номер версии.** Рекомендуется 2.1.0: появляются видимые возможности (магазинная публикация, онбординг, наблюдаемость). Альтернатива 2.0.4 отвергнута как скрывающая масштаб.
- **D4. Ротация токена.** Рекомендуется файловая ротация с рестартом (расширение `ensure_generated_secret`): проще всего, соответствует одной реплике. Hot-reload отвергнут как лишний механизм без требования.
- **D5. CI.** Рекомендуется минимальный конвейер (тесты + сборка + selfcheck + `compose config`) на push/PR. Репо уже живёт на GitHub (ссылки на релизы в `README.md:107`).

## Recommended Approach

Волны с гейтами. Трек публикации — первым (снимает главный внешний блокер и даёт магазинный артефакт для всего остального). Закалка и онбординг — параллельно. Релизный гейт — только после чистой комнаты и CT160-прогона релизного архива (версия неизменяема — ошибаться нельзя). Коммерческий трек ведёт человек и не блокирует технический релиз.

## Work Plan

### Wave 0 — Заморозка (агент, 0.5 дня)

- **T0.1** Зафиксировать D1–D5 решением на этот план; объявить scope freeze (всё вне плана — в Wave 6+).
- **T0.2** Открыть релизную ветку `release/2.1.0` от `main`; дальше — только плановые изменения.
- Приёмка: аппрув плана + ветка создана.

### Wave 1 — Магазинная публикация, P0 (агент + человек на шаге Publish)

- **T1.1 Store-клиент.** Новый `tools/publish_store.py`: `X-Extella-Token` из `~/.extella/os_token.txt`, `my-listings` → `add-version-stream` (поля `version/tags/app_scopes/source_id/page+sha/archive+sha`), сырой SSE — в файл до разбора, терминальные `done/error`, при провале — следующий номер (не тот же), диагностика только именованными полями (H71). Тесты на парсер SSE и ретрай-политику.
- **T1.2 Предрелиз.** Создать/переиспользовать листинг, выложить версию предрелизом (`published=0`), сохранить `listing_id`/`version_id` и SSE-файл как evidence.
- **T1.3 Покупка себе.** Купить точный `version_id` на отдельном агенте-приёмщике (`purchase-stream`, сверить `mode:"new"` в `my-purchases`); проверить `app-archive` (200, побайтовый SHA-256 страницы и архива), скоупы, вызываемость экспертов.
- **T1.4 Чистая комната.** Финальным ZIP: пустой домашний каталог и тома, очищенное окружение Expert, те же маунты; цепочка `не установлено → готово → рестарт → готово`. Dev-smoke с другим PATH не засчитывается.
- Приёмка волны: состояние «предрелиз опубликован, куплен себе, чистая комната пройдена — остался один клик Publish» + evidence-файлы.
- Зависимости: нет. Fallback: при повторной серверной ошибке архива — обход msg22 (публикация без `archive` + bundle-установщик) отдельной задачей с собственной приёмкой.

### Wave 2 — Установка и онбординг, P0 (агент)

- **T2.1 First-bind end-to-end.** Установить, откуда берутся `device_id`/`agent_id` (UI/API/файл), и оформить пошаговый флоу с честными ошибками (включая `extella_device_binding_required` и все коды, встреченные при прогоне); обновить `deploy/README.md`.
- **T2.2 Чистая установка.** Прогон `install.py` + `prepare.py` + `compose up` на чистой машине по документации без импровизаций; зафиксировать транскрипт.
- **T2.3 Linux-заметки.** Требования, отличия от reference-окружения, что негарантировано.
- Приёмка: новый человек ставит продукт по докам с нуля; каждая ошибка объясняет причину и следующий шаг.

### Wave 3 — Прод-закалка, P1 (агент)

- **T3.1 CI.** Конвейер: Python-сюита, Node-сюита, `build_release.py` + сверка хешей, `selfcheck.py`, `compose config -q`. Красный CI блокирует слияние.
- **T3.2 Наблюдаемость и лимиты.** Rate limits на API, access-логи (сохранив H71: без секретов), метрики/расширенный health; доки по алертам.
- **T3.3 Ротация токена.** Процедура + команда/флаг в `prepare.py`, док с drill-шагами и проверкой.
- **T3.4 Бэкапы.** Расписание, заявленные RPO/RTO, drill восстановления из снапшота (с отдельным страховочным бэкапом), обновление `OPERATIONS.md`.
- **T3.5 Compose.** Зажать `agent-zero` (read_only/cap_drop/healthcheck) или зафиксировать документированное исключение с причиной; устранить skew версий образов.
- **T3.6 Ingress-ранбук.** TLS reverse proxy + внешняя авторизация: референсная конфигурация и проверки.
- Приёмка волны: CI зелёный; пробы curl подтверждают лимиты/логи/метрики; drill ротации и восстановления выполнены.

### Wave 4 — Релизный гейт (агент + человек)

- **T4.1 Версия 2.1.0.** Чек-лист: `runtime/product/server.py` (VERSION), `MANIFEST.yaml`, `listing.json`, `deploy/compose.yaml` (теги образов), `tools/build_release.py` (VERSION), регенерация `release-manifest.json`, `automation_passport.yaml`, оба README.
- **T4.2 Полная верификация.** Сюиты, детерминированная пересборка со сверкой хешей, `selfcheck.py`, прогон точного релизного архива на CT160 (тесты + live probe + backup/restore-check).
- **T4.3 Заметки и тег.** Release notes (что вошло, границы, известные ограничения), тег релиза.
- **T4.4 Publish (человек).** `POST /api/listing/{lid}/publish`, затем проверка: `purchase-check`, `app-archive` 200, скоупы, эксперты вызываются.
- Приёмка: все гейты зелёные, листинг видим, evidence-пакеты сохранены.

### Wave 5 — Коммерция и питч, параллельно (человек ведёт, агент поддерживает)

- **T5.1** Права/IP, проценты rev-share, rails/KYC/возвраты, кто платит LLM — письменно (человек).
- **T5.2** Замер run cost и стоимости инфры на релизном контуре (агент).
- **T5.3** Добор deck: конкуренция, GTM, ask, роадмап; устранение цикличности deck ↔ claim-evidence (агент-черновик, человек-финал).
- **T5.4** LOI-пак для 3–5 design partners (человек).
- Приёмка: подписанные/зафиксированные условия + deck без дисклеймерных дыр + измеренные числа.

### Wave 6 — Опционально за гейтом D2 (пост-релиз)

- GSC/OAuth/BYOK-лейны, user-owned E2E, пилотные метрики (time-to-report, accepted recommendations, repeat usage, failures). Входит в релиз только решением на гейте.

## Validation Plan

- **W1:** `python3 tools/publish_store.py --listing ... --version 2.1.0 --save-sse evidence/` → терминальный `done`; `GET /api/listing/{lid}` показывает версию; `purchase-check` ok; `sha256sum` архива/страницы = SHA из шага 2; чек-лист чистой комнаты подписан.
- **W2:** транскрипт чистой установки; матрица ошибок first-bind (каждая — причина + следующий шаг).
- **W3:** зелёный прогон CI; `curl`-пробы лимитов (429), наличие access-логов и метрик; drill ротации (старый токен → 401, новый → 200); `backup.py create/verify/restore-check`; `compose config -q`.
- **W4:** `python3 -m unittest discover -s tests -p "test_*.py"` (ожидается ≥181), `node --test tests/safe_fetch.test.mjs tests/worker_plan.test.mjs tests/ui/ui_contract.test.mjs` (≥64), `build_release.py` + сверка с `dist/build.json`, `selfcheck.py → READY`, CT160: тесты точного архива + `probe.py health/state` + backup; пост-publish проверки магазина.
- **W5:** таблица измеренных затрат; deck-ревью по чек-листу (нет неподтверждённых цифр).
- Самый рискованный шаг: **T1.4 + T4.2** — версия неизменяема (H8), поэтому чистая комната и CT160-прогон релизного архива решают всё до создания версии.

## Risks / Rollback

- Неизменяемость версий (H8): провал → следующий номер, никогда тот же; снять версию — `unlist`/`DELETE`, листинг остаётся; публикация обратима (`published: false`, H26).
- Дрейф контракта выкладки (тел OpenAPI не описывает): пинить ревизию ранбука, всегда сохранять сырой SSE.
- Дефекты платформы (чужое тело листинга видно посторонним): не полагаться как на приватность.
- Откат рантайма: предыдущий архив + биндинги сохраняются; восстановление только с независимым страховочным снапшотом (кросс-вольюмный restore нетранзакционный).
- Человеческий трек (деньги/право) может отстать — он вынесен из критического пути технического релиза.
